## 모바일 전용 일정 이력 5개 병합

원본 5개는 모두 `qa-a25-20261020` 출처의 알림 검증용 일정이며 이미 2026-10-20에 삭제된 상태였다. UI의 로컬 일정 개수에는 삭제된 일정도 포함된다. 병합 시 제목, 날짜, 완료 상태, 생성 시각, 출처, 삭제 시각을 그대로 유지했다. 소유 범위와 결정적 ID는 계정 기준으로 바뀌었고 수정 시각만 병합 시각으로 갱신됐다. 활성 일정으로 복원하지 않았다.

| --- | --- |
| 계정 전체 일정 | 서버·PC·모바일 각각 37개, 모든 일정 필드 일치 |

앱 화면의 “자동 저장됨·동기화됨” 표시뿐 아니라 Windows와 Android의 실제 로컬 저장소 사본에서 최신 스냅샷을 추출해 대조했다. 병합 직후와 재실행 후 모두 전체 일정 37개의 정렬·정규화된 JSON SHA-256은 `f605630efbaee0de9f9a50cc816e32e0169f9536f49ac0feb7358816c0d1971f`로 동일했다. 서버의 날짜/시각 표현은 동일한 시점 기준으로 정규화해 비교했다. 재실행 후 서버 전체 일정도 병합 직후와 변함없었다.

검증용 읽기 도구는 백업 사본만 읽고, CURRENT/MANIFEST의 유효 파일과 시퀀스 번호를 따라 최신 값을 선택하며 로그·테이블 CRC를 검사했다. 재실행 후 데이터가 압축 테이블로 이동한 경우도 포함했다. 형식 확인에는 [LevelDB 로그](https://github.com/google/leveldb/blob/main/doc/log_format.md), [테이블](https://github.com/google/leveldb/blob/main/doc/table_format.md), [Snappy 압축 명세](https://github.com/google/snappy/blob/main/format_description.txt)를 참고했다. 라이브 저장소 직접 편집, DB 직접 쓰기, 재로그인은 하지 않았다.

원본 백업, 병합 전후 및 재실행 후 저장본, 필드별 대조 보고서와 검증 스크립트는 Git에서 제외된 `.codex/deployment-backups/20261107-action-merge/`에 보관했다. `verification-after.json`과 `verification-restart.json`의 판정은 모두 `PASS`다. 원본 백업 및 계정 데이터는 문서나 Git에 포함하지 않았다.

## 관찰된 오류와 검증 한계

재개 직후 모바일에는 이전의 “Supabase Realtime 구독에 실패했습니다.” 안내가 남아 있었다. Fitness 읽기 진단은 정상 상태였고, 이후 PC의 새 메모 수정이 모바일에 자동 반영되면서 오류 안내가 사라졌다. 이어 모바일→PC 수정, 재시작, PC→모바일 삭제 반영까지 성공했다. 이번에 확인한 것은 해당 실행에서의 연결 회복이며, 최초 오류의 원인이나 모든 네트워크 장애에서의 복구를 입증한 것은 아니다. 오류를 감추는 코드 변경은 하지 않았다.

이번 검증은 기존에 게시된 FitnessApp·CashOS 요약의 실제 계정 수신과 온라인 메모 동기화다. 원본 앱에 새 건강·재무 기록을 만들어 게시하는 시험, 네트워크 차단 중 편집·충돌 복구, 다른 계정 간 격리, OS 재부팅 시험은 수행하지 않았다. 재시작 중에도 네트워크를 사용할 수 있었으므로 온라인 재시작 결과를 오프라인 내구성 검증으로 확대하지 않는다. 모바일 로컬 일정 5개의 병합은 위 추가 검증에서 완료했다. 이 5개는 삭제된 이력이므로 활성 일정 5개의 신규 등록을 검증한 것으로 해석하지 않는다.

추가 설치나 애플리케이션 코드 수정은 없었다. 재시작한 Windows 설치본의 SHA-256이 위 배포 파일과 동일함을 다시 확인했다. 문서 변경은 `validate-project-docs.mjs --config project-docs.config.json --require-tracked` 다음 `sync-project-docs-to-notion.mjs --config project-docs.config.json` 순서로 검증하며, 두 번째 명령은 render-only로 실행한다.
